# RMF Payment Gateway — MTN MoMo

RMF processes all money movement over the **MTN Mobile Money (MoMo) API**. PayPack and
Airtel Money have been removed. This document covers configuration, environments, the
payment callback, phone formats, and sandbox testing.

The **internal wallet/escrow architecture is unchanged** — only the transport layer that
actually moves money (collections in, disbursements out) is MTN MoMo.

---

## 1. Two credential sets

MTN MoMo uses **two separate products**, each with its own user id, API secret, and
subscription key. They are NOT interchangeable.

| Purpose | Product | Used by | Credentials |
| --- | --- | --- | --- |
| Buyer pays for an order | **Collections** (Request to Pay) | `order-service` | `MTN_MOMO_COLLECTION_API_KEY`, `MTN_MOMO_COLLECTION_USER_ID`, `MTN_MOMO_COLLECTION_API_SECRET` |
| Seller / rider payout, buyer refund | **Disbursements** (Transfer) | `order-service`, `wallet-service` | `MTN_MOMO_DISBURSEMENT_API_KEY`, `MTN_MOMO_DISBURSEMENT_USER_ID`, `MTN_MOMO_DISBURSEMENT_API_SECRET` |

- `*_API_KEY` is the **Ocp-Apim-Subscription-Key** for that product.
- `*_USER_ID` + `*_API_SECRET` form the Basic-auth credential used to mint an access token
  (`POST /collection/token/` or `POST /disbursement/token/`). Tokens are cached in-process
  for ~1 hour and refreshed ~60 s before expiry.

`order-service` needs **both** sets (collections for checkout, disbursements for refunds).
`wallet-service` needs **only the disbursement set** (withdrawals).

## 2. Sandbox vs production switching

A single variable controls the environment:

| Variable | Sandbox | Production (Rwanda) |
| --- | --- | --- |
| `MTN_MOMO_TARGET_ENV` | `sandbox` | `mtnrwanda` |
| `MTN_MOMO_BASE_URL` | `https://sandbox.momodeveloper.mtn.com` | `https://proxy.momoapi.mtn.com` |

`MTN_MOMO_TARGET_ENV` is also sent as the `X-Target-Environment` header on every call.
If `MTN_MOMO_BASE_URL` is unset, the service derives it from `MTN_MOMO_TARGET_ENV`
(`sandbox` → sandbox URL, anything else → production URL).

When `MTN_MOMO_TARGET_ENV=sandbox` **and** `NODE_ENV !== 'production'`, checkout uses an
auto-confirm dev bypass (no real prompt). This bypass can never activate in production.

Other shared vars: `MTN_MOMO_CURRENCY` (default `RWF`).

## 3. Payment callback

MTN POSTs collection results to the URL set in `MTN_MOMO_CALLBACK_URL`:

```
MTN_MOMO_CALLBACK_URL=https://rmf-order-service.onrender.com/api/v1/orders/payment/mtn/callback
```

- The endpoint is **public** (MTN sends no auth headers) and there is **no HMAC** signature.
- Verification is done by confirming the `referenceId` in the callback maps to a known order
  before any state is mutated. Unknown references are ignored.
- The endpoint **always responds 200** so MTN does not retry indefinitely.
- The callback URL is also passed per-request as the `X-Callback-Url` header on Request to Pay.

Callback / poll body shape:

```json
{
  "referenceId": "uuid-v4-we-sent-as-X-Reference-Id",
  "status": "PENDING | SUCCESSFUL | FAILED",
  "financialTransactionId": "mtn-side-id",
  "externalId": "order.orderNumber"
}
```

`X-Reference-Id` is generated by RMF and **is** the `payment.transactionRef` stored on the
order. The order-service also polls `GET /collection/v1_0/requesttopay/{referenceId}` as a
fallback when callbacks are delayed.

Admins can check configuration health at `GET /api/v1/orders/payment/mtn/readiness`
(admin-only) — it reports which of the 6 credentials are present and whether the callback
URL is set.

## 4. Phone number format

MTN MoMo MSISDN must be `2507XXXXXXXX` (12 digits, no `+`). The shared `normalizeMomoPhone`
helper accepts and normalizes:

| Input | Output |
| --- | --- |
| `07XXXXXXXX` | `2507XXXXXXXX` |
| `2507XXXXXXXX` | `2507XXXXXXXX` |
| `+2507XXXXXXXX` | `2507XXXXXXXX` |
| `7XXXXXXXX` | `2507XXXXXXXX` |

Anything else throws `Invalid Rwanda phone number`.

## 5. Sandbox test numbers

In the MTN sandbox, the payer/payee MSISDN drives the simulated outcome:

| Number | Result |
| --- | --- |
| `+46733123450` | `SUCCESSFUL` |
| `+46733123451` | `FAILED` |

Use the sandbox provisioning script (`scripts/setup-momo-sandbox.js`) to create a sandbox
API user + key, then set the `*_COLLECTION_*` / `*_DISBURSEMENT_*` vars accordingly.

## 6. Withdrawal settlement flow (wallet-service)

1. `availableBalance` is atomically debited and moved to `pendingBalance` (single
   `findOneAndUpdate` with an `availableBalance >= amount` precondition — no double-spend).
2. `POST /disbursement/v1_0/transfer` is called. On HTTP 202 the payout request is set to
   **`PROCESSING`** (not `COMPLETED`).
3. A background poller checks `GET /disbursement/v1_0/transfer/{referenceId}` every 30 s,
   up to 10 times:
   - `SUCCESSFUL` → payout request `COMPLETED`, `pendingBalance` decremented, `totalWithdrawn` increased.
   - `FAILED` → payout request `FAILED`, amount returned to `availableBalance`, `pendingBalance` decremented.

Money is only considered settled after MTN confirms the transfer.

## 7. Environment variable reference

`order-service`: `MTN_MOMO_COLLECTION_API_KEY`, `MTN_MOMO_COLLECTION_USER_ID`,
`MTN_MOMO_COLLECTION_API_SECRET`, `MTN_MOMO_DISBURSEMENT_API_KEY`,
`MTN_MOMO_DISBURSEMENT_USER_ID`, `MTN_MOMO_DISBURSEMENT_API_SECRET`, `MTN_MOMO_TARGET_ENV`,
`MTN_MOMO_BASE_URL`, `MTN_MOMO_CALLBACK_URL`, `MTN_MOMO_CURRENCY`, `ADMIN_USER_ID`,
`DISABLE_MOCK_AUTH`.

`wallet-service`: `MTN_MOMO_DISBURSEMENT_API_KEY`, `MTN_MOMO_DISBURSEMENT_USER_ID`,
`MTN_MOMO_DISBURSEMENT_API_SECRET`, `MTN_MOMO_TARGET_ENV`, `MTN_MOMO_BASE_URL`,
`MTN_MOMO_CURRENCY`, `ESCROW_RELEASE_DELAY_HOURS`, `DISABLE_MOCK_AUTH`.

All credential vars are `sync: false` in `render.yaml` (set manually in the Render
dashboard, never committed).
